## 0. 读法与纪律

**核验口径**：一条结论成立与否，看的是「源码里有没有那条路径」，
不是「文档里有没有那句承诺」。本文沿用评审里最有价值的两条区分：

- **契约**（声明应该怎样）与**执行**（实际怎样）分开判——
  「注释写了不许」不等于「代码拦得住」；
- **机制面**（与「谁在用它」无关）归本仓，**装配面**（谁接哪个后端）归宿主。

**引用口径**：本文代码引用写到 `文件:行`，对应基线 `fdc4922`。
本文**不抄会过期的数字**（覆盖率、规则条数、包数一律以门禁输出为准）——
抄进来就是给自己造一份会静默过期的真相。

## 1. 一句话结论

内核的**机制密度已经够了**：认领唯一性、令牌铸造、幂等闸、单调进度、
代次、Handoff、故障注入矩阵都在。缺的不是模块，是**闭环**——
身份的作用域、租约的续期、事件的可靠交付、资源的回收、权威的唯一。

下一阶段的主题因此不是「再加机制包」，而是把**声明的保证变成可证明的保证**。

## 3. 三条硬事实（基线判断，**已被本轮成果推翻**）

> **读法**：这一节记录的是**基线 `fdc4922` 当时的信息长什么样**，它是「判断是怎么形成的」
> 的证据。**三条现在都已不成立**——不要把它当现状读。每条后面给出现在的落地位置。

**（a）当时：契约不是兑现。** TailStore 的「无空洞推进」写得很硬，但仓内没有任何
生产实现满足它——连 pgstore 都没有事件表。评审问的是「PostgreSQL 会不会自动
满足契约」，真问题是「**那个实现还没人写**」。差别决定工作量：前者改 SQL，
后者写一个面。

> **现在（#264 已合入）**：`examples/pgstore/event.go` 落地了 Outbox 形态参考实现——
> `pgref_event_watermark` 单行水位表作分配串行化点（UPDATE…RETURNING 拿号持行锁到提交
> ⇒ 铸造序 == 提交序），`PublishInTx` 与业务状态同事务，读侧 `CommittedWatermark`
> 只报**已提交**水位线。契约与实现现在同源。

**（b）当时：参考实现缺面，比实现有 bug 更危险。** pgstore 只有 5 张表
（effect_action / effect_resource / downstream / board_task / snapshot），
**没有事件表、没有租户列、没有 `controlplane.Store`**。宿主照抄 schema 会
以为「PG 面齐了」，然后在自己的实现里把三处空白各填一次——各填一次就各漂一次。

> **现在（#275 / #278 已合入）**：pgstore 现有 **11 张表**（新增事件表 / 事件水位线 / 尾随游标 /
> 运行记录 / 控制面版本锚 / 控制面效果行），事件表与 effect 表带**租户维度**，
> `ControlStore` 实现了 `controlplane.Store` 且**复用 `pgref_board_task` 作为唯一可写
> 任务状态**（`TaskSourceID` 同源判定 ⇒ 装配期判「同一张任务表」，
> 不同源即 `ErrAuthorityMismatch`）。三处空白都填上了，且填在**同一处**。

**（c）当时：门禁骨架已在，扩展成本低。** `worker/faultmatrix` 已经是
「故障类 × 部署模式」的可执行矩阵（6 类 × 3 模式），自检规则是
「每类至少一条用例，漏一类即红」。评审要的 8 个新场景**扩行扩列即可**，
不需要另起炉灶。

> **现在（#274 已合入）**：矩阵从 6 类扩到 **14 类**，新增 8 类各有独立用例文件
> （`k8s_response_test.go` / `tenant_test.go` / `longlease_test.go` /
> `dbfailover_test.go` / `eventreorder_test.go` / `quota_test.go` /
> `controlrace_test.go` / `networkpolicy_test.go`）。「扩列即可」的判断被验证成立——
> 扩的是行（用例）与列（必有余量登记），**没有另起炉灶**。
> 但扩列也暴露了「只准扩不准删」这条纪律的另一半：**只登记 `requiredMatrixCells`
> 不够**，类名本身也要有不可删除的登记位，否则新增类可以悄悄被删掉而不红。
## 4. 演进路线（**三阶段已全部达成**）

> **状态**：L1 / L2 / L3 的 18 条单（#261–#278）已全部合入主干并关闭。
> 本节保留为**目标态定义**（每条改动的归谁与可机判验收），外加一列落地位置——
> 读者要判断「这条现在到底有没有做」，看落地位置那一列，不要看单号。

### L1 · 身份与租约闭环（P0/P1，机制面主要在本仓）✅ 已达成

目标：任何一次执行都有**唯一身份**；任何一段长执行都**不会在租约过期后仍能提交状态**。

| 机制面改动 | 归谁 | 可机判验收 | 落地位置 |
|---|---|---|---|
| 动作身份规范 + `ActionKeyBuilder`（Tenant + Run + Task + Action；**Attempt 不入键**） | 本仓（sideeffect / worker） | 两租户同 TaskID、同动作参数 ⇒ 无重放、无冲突；同租户不同 Run 同 TaskID ⇒ 同上 | `sideeffect/key_scope.go` |
| 受管租约会话（`LeaseSession`：Context / Token / Fence / AssertOwned） | 本仓（worker + taskboard） | 执行超过 TTL 后，旧持有者的 Checkpoint / Complete 被**存储端条件提交**拒绝 | `worker/managed.go` + `checkpoint/fence.go`（`SaveIfNewerFenced` / `CommitFenced`） |
| 续期调度改为按绝对到期时间 + 并发上限 + 批量续期 | 本仓（worker + taskboard 门面） | 200 在途、续期 100ms/条、TTL 15s ⇒ 无一任务在续期前失格 | `worker/heartbeat.go` |
| 游标初始化契约修正（found=false ⇒ 显式起点 ⇒ MaxID） | 本仓（eventbus） | 组合用例 `CursorStore(empty) + StartCursor(100)` ⇒ 从 100 起读 | `eventbus/tail.go` |

出口条件：上表四条验收全绿 ⇒ 「一个动作至多施加一次、一次执行至多提交一次进度」
在多副本形态下**可证**，而不是「按约定应该」。

### L2 · 可靠交付与资源回收 ✅ 已达成

目标：事件不丢、配额不漏、控制面与执行面同账、租户隔离落到存储。

- **可靠事件面**：Outbox / 水位线语义的**生产级 TailStore 参考实现**
  ＋ 事件写入与业务状态同事务 ⇒ `examples/pgstore/event.go`（#264）；
- **终态同事务**：终态写入 + 终态事件同一事务，投递失败走 Outbox 补做
  ⇒ `reconcile/finalize.go`（Finalize Intent + Outbox，#272）；
- **配额回收**：`QuotaLease` 带 TTL / Owner / 关联 Task；回收走 Reconciler，
  且**必须先确认任务租约已失效**——不能凭「心跳消失」就归还额度，否则旧任务
  可能还在真跑 ⇒ `scheduling`（#267）；
- **权威统一**：控制面强制释放 / 裁决走**同一份任务记录**，不构造第二份可写任务状态
  ⇒ `controlplane/authority.go` + `examples/pgstore/control.go`（#268 / #278）；
- **租户隔离落到持久化面**：effect / 事件表加租户维度 ⇒ `examples/pgstore/schema.go`（#275）；
- **租约窗口误差预算**：判定时刻—提交时刻的窗口变成可查事实（原子后端窗口 0，
  非原子后端走误差预算降级路径并显式标记）⇒ `coord/precision.go`（#271）。

出口条件：事件乱序提交不丢帧；配额悬挂可安全回收；控制面并发介入只有一次有效状态转换。

### L3 · 跨域所有权 ✅ 已达成

目标：跨区域多集群下不出现双主执行。

- 按区域定义**唯一 Ownership Authority**，跨区域转移用 Epoch + 确认协议
  ⇒ `ownership/`（`BeginTransfer` 只记录候选代次、**不改变**当前权威；
  `ConfirmTransfer` 换代是一次原子操作：代次提升 + 区域切换 + 令牌重铸）；
- 网络分区期间旧域写入被 fence **拒绝**（不是「尽量」拒绝）：
  旧代提交一律 `ErrStaleEpoch`、确认前的候选代次一律 `ErrEpochUnconfirmed`；
- 场景化部署配方固化为**可执行的能力清单** ⇒ `docs/DEPLOY-MATRIX.yaml` +
  `cmd/deploymatrix/`（#277）：状态由证据推导，不手写会过期的结论。

### 第四阶段候选面（三阶段已合入 ⇒ 题不再是「补机制」）

1. **接缝契约三条成文 + 机判**：所有宿主接缝统一写明「不得重入 / 不得阻塞 / panic 不外溢」。
   当前 `architecture-policy.yaml` 里**没有任何一条规则**查「接缝是否在锁内被调」——
   第三轮修的 5 处（#317 / #326 / #327 / #328 / #329）全靠人读，下一次回涨拦不住；

3. **未知态的方向判据**：凡是把「未知」压成一个已知值的判定面，都要判一次「沉默落在哪一侧」，

## 7. 本轮明确不做（防范围蔓延）

- **不**引入 client-go：K8s 面继续零依赖手写 HTTP（依赖面纪律见 ADR-0003）；
- **不**引入 SQLite 驱动：examples 不给主 module 增传递依赖树
  （理由见 `examples/sqlitestore/doc.go`）；
- **不**在本仓实现「宿主部署拓扑」判据：拓扑归宿主，机制归本仓；
- **不**做跨地域双主：L3 的前置是 L1 + L2；
- **不**把 examples 参考实现的完备性当成本仓门禁对象：参考实现是**给宿主抄的契约**，
  不是判定面（真 PG 契约由 `make integration` 承担）。

## 8. 落地纪律（每条演进都要满足）

1. **判据先于实现**：机制面改动必须带「坏实现会红」的用例——只测「好实现能过」的
   用例，一个把数字比较写成字符串比较的错实现照样全过；
2. **门禁接线**：新判据接进 `make check`，不只挂在 CI 工作流上；
3. **文档数字有主**：可机判的数字交给门禁输出，本文不抄；
4. **反向验证**：契约类改动（TailStore、幂等键、租约）必须带**违约实现**的对照用例。

### 这一轮反复出现的五个形态（比单条缺陷更值得记住）

**（a）判定面是对的，出口是弱的。** `deadline.Config.Begin` 内部**确实调了** `Anchor.State(now)` 这个三态判定面，
却只把「expired」一态传出去（#318）；`tooldisclose.Catalog` 内部**确实按**「目录成员构造后不再变化」这条不变式组织，
却在四个出口把内部的 map/slice 直接交出（#316）。共同形态是**内部知道得比出口多**——于是出现
「内部正确 + 出口缺信息」。这类缺陷光看实现看不出来，因为实现本身是对的；**要问出口给了什么**。

**（b）同一个事实、同一个输入、两条相反的判据，而且都在同一个包里。** `protocol` 的 `scope`：解析面改成 `in`、
校验面判 critical（#321）；`taskboard` 的状态：`Check` 报 `unknown_state`、`Claim` 照认（#323）；
`statemachine` 的环节类别：`CanTransition` 拒、`RequiresApproval` 免审（#322）；`controlplane` 的留痕：
`StorePlane` 锁外、`MemStore` 锁内（#327）。本仓「机制单源」讲的是**判据**单源，
而这四条说明**同一判据的两处实现**也会分叉——形态相同、方向相同（多数是其中一侧更松）。

**（c）「未知当否」的方向问题：沉默必须落在安全的那一侧。** `scope` 词表外改成 `in`（**更宽**）、
`severity` 大小写变体成 rank 0（**更轻**）、词表外任务状态当可领（**放行执行**）。三条的失效方向惊人一致：
**都朝着「看起来更没问题」那一侧偏**。这不是巧合——把未知压成一个已知值时，人们默认压成「最常见的那一档」，
而最常见的那一档往往不是最保守的那一档。判定面问的问题应是「**沉默落在哪一侧**」，不是「有没有处理未知」。

**（d）参考实现不是豁免区，「形态示范」更不是。** `ticket` / `handoff` / `worker` 三个参考实现都在锁内调宿主注入的时钟回调（#317）；
`controlplane.MemStore` 的包头**自己写着**「给宿主当形态示范」（#327）。参考实现的职责是「证明契约可满足」，
而它恰恰在契约最核心的一格（时间权威在存储侧 / 留痕与状态同事务）上否掉了自己。

**（e）同一件事两个包各写一份，互不认领。** `deadline` 与 `finalize` 各有一份 `ErrSessionDeadline`——**同文案、不同 error 值**（#333）。
内核自己装 ctx、内核自己收尾，一组合就复现了它俩**注释里都点名要防**的失败形态：墙钟超时被收尾侧判成停机 ⇒
不落终态 ⇒ 会话永久滞留 running。「同名同文案但不同值」这种形态肉眼极难发现（grep 出来两行一模一样），
却能让两个包**对同一个 ctx 给出相反结论**。⇒ 门禁面的一条空白：全仓「相同文案的 `errors.New` 出现多次」目前无人判。

### 复核手段（这一轮的方法，与结论同等重要）

1. **机械检索出候选全集**：横切面三用自写 AST 扫描器（词法锁区间 + **同包调用图污点传播**），
   因为「持锁调本包函数 → 该函数调接缝」这一形态只查词法会整类漏掉；
2. **用已知种子反向校准扫描器**：种子是第二轮已开的 `trajectory` #302（`Options.Summarize` 在 `p.mu` 内）。
   **首版扫描器把 `defer Unlock()` 当成即时释放 ⇒ 种子漏报**——校准这一步救回整轮结论；
3. **实测三种形态**：仓外临时模块（`replace` 指向本仓，测导出 API 的真实行为）、
   `go test -overlay`（虚拟注入用例，**仓内零落盘**）、`go test -race`（抓数据竞争）；
4. **每个结论都要能贴出可复现的输出**：死锁贴阻塞栈、竞态贴 race 报告、别名改穿贴改前改后的值。

### 这一轮新出现的五个形态（比单条缺陷更值得记住）

**（a）接缝的「契约」可以完全不存在，而它不被当成缺陷。** 生产代码 20 个时钟接缝里，
**0 个**写齐「不得重入 / 不得阻塞 / panic 隔离」；写齐的 3 个**恰好都是 #317 被逼着修过的那几处**
（`ticket` / `handoff` / `worker`）。⇒ 纪律只存在于**被修过的地方**，新接缝按「直觉写」就是一句话散文。
根因不是「写漏了」，是**没人被要求写**：没有清单、没有模板、没有门禁（#369 / #370）。

**（b）越权可以由「拷贝不安全」造成，而不需要任何逻辑错误。** `tenant.Context` 的授权面被别名改穿 ⇒
`Require(ctx, "admin")` 放行。深拷贝从「承诺」查到「字段」这一面，最重的**不是数据竞争，是授权面被改穿**。
而且仓内那条守护它的断言用 `append`（`len==cap==1` ⇒ append 必然重分配 ⇒ **结构上不可能改穿**）
⇒ 在「是否别名」两种实现下**都绿** ⇒ 假绿（#376）。

**（c）修好一条通路，会让下游的旧缺口第一次变成活缺口。** #58（第三轮）修好了 `rejectionKindOf`——
**探测面**——于是 `*toolfail.Failure` 的分类**第一次**能流到 `res.ErrorKind`；
而 `kindForErrorKind`——**映射面**——的 case 清单从未同步接住这条新通路 ⇒
9 个 toolfail 分类里 8 个被丢弃成 `unknown`（#364）。⇒ 任何新增的分类/状态出口，
必须同时检查**所有消费它的判据表**，而不只是出口本身。

**（d）契约指向宽松的那份，实现按严格的那份判。** `controlplane.Auditor`：`audit.go:39` 说
「词表见 Action\* 常量」（4 值，含 `ActionQuery`），实现却按私有 3 值判 ⇒ `ActionQuery` 被拒；
词表外动作在参考实现侧被拒、在宿主侧被收。⇒ 宿主按契约实现**就是错的**，
而内核参考实现与宿主对同一条留痕给出**相反结论**。⇒ 理由被写在了**错误的一侧**
（解释在私有实现的注释里，契约侧没有）（#372）。

**（e）「声明了但做不到」与「根本没声明」在本仓是同一种病，成本差一个量级。**
`statemachine.IsTerminal` 的注释承诺「词表以转移表为准」，代码不读表（#374）；
`taskboard.StateFailed` 的常量注释说「终态」，`Terminal()` 说只有 done 是（#375）。
这类缺陷当前**无运行时失效**，但它们是**下一位维护者的第一入口**——
而维护者读到的正是注释。按本仓纪律「声明与实现不符仍算缺陷」，它们独立成立。

### 这一轮新出现的五个形态（比单条缺陷更值得记住）

**（a）门禁的「负对照」自己也会有覆盖盲区。** `examples:` 机制的设计是对的
（一正一反、共用真实判定核、加载期断言），但它只要求「有正例有反例」，
**不要求覆盖正则的每个分支**。于是 `harness-single-errors-package` 的
`^github\.com/pkg/errors$` 那一半**没有任何样例** ⇒ 删掉它，`examples:` 全绿、
加载期自校验全绿、门禁全绿。⇒ **上一轮「门禁自己也要能被检查」只查到了「规则有没有执行体」，
这一轮才查到「执行体的覆盖是否完整」**——门禁的负对照也需要**按分支**覆盖，
而不是「有正有反各一条」就够。

**（b）假绿有三种形状，且都读起来像在守护。** ①断言手法在坏实现下**不可能触发**
（`append` vs 下标赋值，#387）；②断言的源对象与被测对象**类型不兼容**
（`[]StepDef` vs `[]string`，#393）；③断言的点名对象**从未出现在用例里**
（`Rows()` 用例根本没构造投影器，#388）。
共同点：**用例里出现了那个符号，不等于用例守住了那个符号的契约**。
⇒ 「断言文案点名了某个 API」是**最不可信**的信号。

**（c）词表不同步的失效方向是**双向**的。** 前几轮深拷贝的失效方向多是「更松（改穿）」；
这一轮 `reconcile` → `watchdog` 的归因词表是**更严（假红）**：
生产方 4 个取值消费方只认 2 个，被成功归因的收敛路径被判成「无归因」（#391）。
⇒ 「两份词表不一致」既可能放过非法值，也可能把**合法值**判成非法；
而后者更隐蔽 —— 它不产生非法状态，只产生噪声，于是被当成「宿主注册词表没填全」。

**（d）缺省词表会违反它自己声明的不变式。** `watchdog.Config.ClosedBy` 的注释写明
「缺省四值是所有宿主共有的收尾路径，只增不减才能避免『宿主少写一个值就把合法归因判成红』」——
而缺省四值**自己**漏了 `reconcile` 的两条（#391）。
⇒ **自述的不变式需要机判**，否则它只是**愿望**：注释里写「只增不减」的那张表，
正是最可能悄悄少一项的地方。

**（e）同一包内两个宿主接缝的 panic 口径可以相反。** `eventbus` 的 `onDrop`
走 `subhub.Do` 隔离（issue #328 已修），`Store.Insert` 在同一个发布临界区里**不隔离**；
而 `internal/subhub` 的包头不变量明写「回调 panic 不得影响发布面」（#399）。
⇒ 「这个包已经处理过 panic 隔离」这句话，**只对被显式修过的那一个接缝成立**；
同包的第二个接缝不会自动继承。

### 复核手段（这一轮的方法，与结论同等重要）

1. **机械探针先做反向校准，才准它出「无问题」清单**：本轮接缝扫描器的原定校准种子
   （#366 / #367 的锁内时钟接缝）**已被修掉**，于是改用「把已修形态注入临时副本」的合成种子，
   三种形态（多出口解锁 / helper 跨函数 / 闭包 defer）必须全部命中才继续。
2. **子代理只读当前工作树 + 每条引用打印该行实际内容**（沿用上一轮纪律）。
   本轮子代理的扫描器**自己暴露了两个缺陷**（方法形式 helper 漏判、callee key 空间不一致），
   都是靠「注入已知种子必须命中」这一步抓出来的 ⇒ **校准步骤的价值不在于确认结论，
   而在于暴露工具自己的 bug**。
3. **主会话逐条复现，不直接采信**：16 条带实测输出的单**全部由主会话亲跑**
   （overlay 变异、仓外探针、仓外临时目录跑真实门禁 CLI）。
4. **反向验证成对，且反向验证本身要有阳性对照**：本轮 8 个变异体里，7 个让整包**仍绿**（假绿坐实），
   而 `checkpoint` 的同族变异让整包**转红**（`TestZeroValueMatchesLegacyOracle`）
   ⇒ 证明「整包仍绿」不是因为工具有别的问题。
5. **探针自身的失败要归因到夹具，不是判据**：`cmdpolicy` 探针首跑被 policy 自检拦下
   （NotMatch 样例写错 ⇒ 规则判据比声明宽）⇒ 是**夹具**错；`memorypipe` 探针首跑条目未被选中
   （漏填 `Source`）⇒ 也是**夹具**错。两次都先修夹具再下结论——
   否则就会把「我的探针写错了」写成一条缺陷单。
6. **否掉自己最初的判断也要写进台账**：本轮自选面最初判断「9 条规则里 7 条无负对照」，
   查证后**否掉**（`examples:` 机制本来就是负对照），
   改从「覆盖了哪个分支」重新切入才找到真缺口（形态 a）。
   ⇒ **审计方法本身也要被审计**：一个「看起来像结论的中间判断」可能只是没查到底。

### 数字纪律（本轮新增的一条自律）

本轮出现的统计（**214** 个接缝声明 / **562** 个调用点 / **写齐 0 个**）来自类型感知扫描器，
主会话**未逐条复核全部 214 条**。按 AGENTS.md 的纪律，这些数字**只作为扫描器输出**出现在
issue 正文里（#400），**不抄进本文档正文**；若将来要进文档，必须先把它接成机判
（#400 的验收标准已经写好：扫描器集合与门禁登记集合逐条相等，缺一即红）。

### 下一轮（第六阶段）建议（按面，不按单）

1. **判据的覆盖本身要被机判**：把形态 a 与形态 b 做成两条门禁自校验口径——
   「每条规则的每个正则分支至少一条样例」（#386）与
   「守护用例必须真的触达它点名的对象」（#387 / #388 / #393）。
   这两条一旦落地，**假绿与门禁盲区就都从「靠人记得做反向验证」变成「漏了必红」**；
2. **反向验证的阳性对照机制化**：门禁里加一条自检——「故意造一个坏实现 ⇒ 必须有测试转红」，
   即**测试集对自身的鉴别力**。否则「整包仍绿」与「工具放水」永远分不开（本轮靠人工比对才分开）；
3. **词表同步做成通用规则**：凡某包导出「值域常量」，消费包必须**引用**它而非手抄；
   生产方导出集合 ⊇ 消费方认领集合（#391 的形态）应有一条通用判据，
   而不是逐对人工核对；
4. **深拷贝第三轮要收窄范围**：本轮子代理如实列出——**927 个出口里 793 个未逐个查**，
   且**接口字段与 func 字段未纳入别名面**。下一轮要么把范围收窄到
   **授权面 / 裁决面 / 审计面**（这三类的别名后果不可逆），要么把扫描器固化成门禁；
5. **接缝清单固化**：#400 的 214 条接缝清单应当变成**机判清单**（缺一即红），
   与 #370 的 `@seam:` 标记合并成同一份——两份清单各说一半时，
   「接缝到底有多少个」会继续没有答案。
