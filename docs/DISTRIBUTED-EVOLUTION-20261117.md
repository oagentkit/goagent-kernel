## 0. 读法与纪律

**核验口径**：一条结论成立与否，看的是「源码里有没有那条路径」，
不是「文档里有没有那句承诺」。本文沿用评审里最有价值的两条区分：

- **契约**（声明应该怎样）与**执行**（实际怎样）分开判——
  「注释写了不许」不等于「代码拦得住」；
- **机制面**（与「谁在用它」无关）归本仓，**装配面**（谁接哪个后端）归宿主。

**引用口径**：本文代码引用写到 `文件:行`，对应基线 `fdc4922`。
本文**不抄会过期的数字**（覆盖率、规则条数、包数一律以门禁输出为准）——
抄进来就是给自己造一份会静默过期的真相。

## 1. 一句话结论

内核的**机制密度已经够了**：认领唯一性、令牌铸造、幂等闸、单调进度、
代次、Handoff、故障注入矩阵都在。缺的不是模块，是**闭环**——
身份的作用域、租约的续期、事件的可靠交付、资源的回收、权威的唯一。

下一阶段的主题因此不是「再加机制包」，而是把**声明的保证变成可证明的保证**。

## 3. 三条硬事实（基线判断，**已被本轮成果推翻**）

> **读法**：这一节记录的是**基线 `fdc4922` 当时的信息长什么样**，它是「判断是怎么形成的」
> 的证据。**三条现在都已不成立**——不要把它当现状读。每条后面给出现在的落地位置。

**（a）当时：契约不是兑现。** TailStore 的「无空洞推进」写得很硬，但仓内没有任何
生产实现满足它——连 pgstore 都没有事件表。评审问的是「PostgreSQL 会不会自动
满足契约」，真问题是「**那个实现还没人写**」。差别决定工作量：前者改 SQL，
后者写一个面。

> **现在（#264 已合入）**：`examples/pgstore/event.go` 落地了 Outbox 形态参考实现——
> `pgref_event_watermark` 单行水位表作分配串行化点（UPDATE…RETURNING 拿号持行锁到提交
> ⇒ 铸造序 == 提交序），`PublishInTx` 与业务状态同事务，读侧 `CommittedWatermark`
> 只报**已提交**水位线。契约与实现现在同源。

**（b）当时：参考实现缺面，比实现有 bug 更危险。** pgstore 只有 5 张表
（effect_action / effect_resource / downstream / board_task / snapshot），
**没有事件表、没有租户列、没有 `controlplane.Store`**。宿主照抄 schema 会
以为「PG 面齐了」，然后在自己的实现里把三处空白各填一次——各填一次就各漂一次。

> **现在（#275 / #278 已合入）**：pgstore 现有 **11 张表**（新增事件表 / 事件水位线 / 尾随游标 /
> 运行记录 / 控制面版本锚 / 控制面效果行），事件表与 effect 表带**租户维度**，
> `ControlStore` 实现了 `controlplane.Store` 且**复用 `pgref_board_task` 作为唯一可写
> 任务状态**（`TaskSourceID` 同源判定 ⇒ 装配期判「同一张任务表」，
> 不同源即 `ErrAuthorityMismatch`）。三处空白都填上了，且填在**同一处**。

**（c）当时：门禁骨架已在，扩展成本低。** `worker/faultmatrix` 已经是
「故障类 × 部署模式」的可执行矩阵（6 类 × 3 模式），自检规则是
「每类至少一条用例，漏一类即红」。评审要的 8 个新场景**扩行扩列即可**，
不需要另起炉灶。

> **现在（#274 已合入）**：矩阵从 6 类扩到 **14 类**，新增 8 类各有独立用例文件
> （`k8s_response_test.go` / `tenant_test.go` / `longlease_test.go` /
> `dbfailover_test.go` / `eventreorder_test.go` / `quota_test.go` /
> `controlrace_test.go` / `networkpolicy_test.go`）。「扩列即可」的判断被验证成立——
> 扩的是行（用例）与列（必有余量登记），**没有另起炉灶**。
> 但扩列也暴露了「只准扩不准删」这条纪律的另一半：**只登记 `requiredMatrixCells`
> 不够**，类名本身也要有不可删除的登记位，否则新增类可以悄悄被删掉而不红。
## 4. 演进路线（**三阶段已全部达成**）

> **状态**：L1 / L2 / L3 的 18 条单（#261–#278）已全部合入主干并关闭。
> 本节保留为**目标态定义**（每条改动的归谁与可机判验收），外加一列落地位置——
> 读者要判断「这条现在到底有没有做」，看落地位置那一列，不要看单号。

### L1 · 身份与租约闭环（P0/P1，机制面主要在本仓）✅ 已达成

目标：任何一次执行都有**唯一身份**；任何一段长执行都**不会在租约过期后仍能提交状态**。

| 机制面改动 | 归谁 | 可机判验收 | 落地位置 |
|---|---|---|---|
| 动作身份规范 + `ActionKeyBuilder`（Tenant + Run + Task + Action；**Attempt 不入键**） | 本仓（sideeffect / worker） | 两租户同 TaskID、同动作参数 ⇒ 无重放、无冲突；同租户不同 Run 同 TaskID ⇒ 同上 | `sideeffect/key_scope.go` |
| 受管租约会话（`LeaseSession`：Context / Token / Fence / AssertOwned） | 本仓（worker + taskboard） | 执行超过 TTL 后，旧持有者的 Checkpoint / Complete 被**存储端条件提交**拒绝 | `worker/managed.go` + `checkpoint/fence.go`（`SaveIfNewerFenced` / `CommitFenced`） |
| 续期调度改为按绝对到期时间 + 并发上限 + 批量续期 | 本仓（worker + taskboard 门面） | 200 在途、续期 100ms/条、TTL 15s ⇒ 无一任务在续期前失格 | `worker/heartbeat.go` |
| 游标初始化契约修正（found=false ⇒ 显式起点 ⇒ MaxID） | 本仓（eventbus） | 组合用例 `CursorStore(empty) + StartCursor(100)` ⇒ 从 100 起读 | `eventbus/tail.go` |

出口条件：上表四条验收全绿 ⇒ 「一个动作至多施加一次、一次执行至多提交一次进度」
在多副本形态下**可证**，而不是「按约定应该」。

### L2 · 可靠交付与资源回收 ✅ 已达成

目标：事件不丢、配额不漏、控制面与执行面同账、租户隔离落到存储。

- **可靠事件面**：Outbox / 水位线语义的**生产级 TailStore 参考实现**
  ＋ 事件写入与业务状态同事务 ⇒ `examples/pgstore/event.go`（#264）；
- **终态同事务**：终态写入 + 终态事件同一事务，投递失败走 Outbox 补做
  ⇒ `reconcile/finalize.go`（Finalize Intent + Outbox，#272）；
- **配额回收**：`QuotaLease` 带 TTL / Owner / 关联 Task；回收走 Reconciler，
  且**必须先确认任务租约已失效**——不能凭「心跳消失」就归还额度，否则旧任务
  可能还在真跑 ⇒ `scheduling`（#267）；
- **权威统一**：控制面强制释放 / 裁决走**同一份任务记录**，不构造第二份可写任务状态
  ⇒ `controlplane/authority.go` + `examples/pgstore/control.go`（#268 / #278）；
- **租户隔离落到持久化面**：effect / 事件表加租户维度 ⇒ `examples/pgstore/schema.go`（#275）；
- **租约窗口误差预算**：判定时刻—提交时刻的窗口变成可查事实（原子后端窗口 0，
  非原子后端走误差预算降级路径并显式标记）⇒ `coord/precision.go`（#271）。

出口条件：事件乱序提交不丢帧；配额悬挂可安全回收；控制面并发介入只有一次有效状态转换。

### L3 · 跨域所有权 ✅ 已达成

目标：跨区域多集群下不出现双主执行。

- 按区域定义**唯一 Ownership Authority**，跨区域转移用 Epoch + 确认协议
  ⇒ `ownership/`（`BeginTransfer` 只记录候选代次、**不改变**当前权威；
  `ConfirmTransfer` 换代是一次原子操作：代次提升 + 区域切换 + 令牌重铸）；
- 网络分区期间旧域写入被 fence **拒绝**（不是「尽量」拒绝）：
  旧代提交一律 `ErrStaleEpoch`、确认前的候选代次一律 `ErrEpochUnconfirmed`；
- 场景化部署配方固化为**可执行的能力清单** ⇒ `docs/DEPLOY-MATRIX.yaml` +
  `cmd/deploymatrix/`（#277）：状态由证据推导，不手写会过期的结论。

### 第四阶段候选面（三阶段已合入 ⇒ 题不再是「补机制」）

1. **接缝契约三条成文 + 机判**：所有宿主接缝统一写明「不得重入 / 不得阻塞 / panic 不外溢」。
   当前 `architecture-policy.yaml` 里**没有任何一条规则**查「接缝是否在锁内被调」——
   第三轮修的 5 处（#317 / #326 / #327 / #328 / #329）全靠人读，下一次回涨拦不住；

3. **未知态的方向判据**：凡是把「未知」压成一个已知值的判定面，都要判一次「沉默落在哪一侧」，
   并把「更松 / 更宽 / 更轻」的方向标出来；
4. **深拷贝从「承诺」查到「字段」**：把**所有含 map/slice 字段的导出结构体**列出来，逐个查它的每个出口；
5. **词表单一来源**：内核词表已可导出（#320），README 两张手抄表已接进机器判据（#314 / #315），

1. 需要真集群的格**必须填 `matrixCase.requiresEnv`**（显式 `Skipf` + 打印所需环境），

### 这一轮反复出现的五个形态（比单条缺陷更值得记住）

**（c）「未知当否」的方向问题：沉默必须落在安全的那一侧。** `scope` 词表外改成 `in`（**更宽**）、

### 这一轮新出现的五个形态（比单条缺陷更值得记住）

**（a）接缝的「契约」可以完全不存在，而它不被当成缺陷。** 生产代码 20 个时钟接缝里，
**0 个**写齐「不得重入 / 不得阻塞 / panic 隔离」；写齐的 3 个**恰好都是 #317 被逼着修过的那几处**
（`ticket` / `handoff` / `worker`）。⇒ 纪律只存在于**被修过的地方**，新接缝按「直觉写」就是一句话散文。
根因不是「写漏了」，是**没人被要求写**：没有清单、没有模板、没有门禁（#369 / #370）。

**（b）越权可以由「拷贝不安全」造成，而不需要任何逻辑错误。** `tenant.Context` 的授权面被别名改穿 ⇒
`Require(ctx, "admin")` 放行。深拷贝从「承诺」查到「字段」这一面，最重的**不是数据竞争，是授权面被改穿**。
而且仓内那条守护它的断言用 `append`（`len==cap==1` ⇒ append 必然重分配 ⇒ **结构上不可能改穿**）
⇒ 在「是否别名」两种实现下**都绿** ⇒ 假绿（#376）。

**（c）修好一条通路，会让下游的旧缺口第一次变成活缺口。** #58（第三轮）修好了 `rejectionKindOf`——
**探测面**——于是 `*toolfail.Failure` 的分类**第一次**能流到 `res.ErrorKind`；
而 `kindForErrorKind`——**映射面**——的 case 清单从未同步接住这条新通路 ⇒
9 个 toolfail 分类里 8 个被丢弃成 `unknown`（#364）。⇒ 任何新增的分类/状态出口，
必须同时检查**所有消费它的判据表**，而不只是出口本身。

**（d）契约指向宽松的那份，实现按严格的那份判。** `controlplane.Auditor`：`audit.go:39` 说
「词表见 Action\* 常量」（4 值，含 `ActionQuery`），实现却按私有 3 值判 ⇒ `ActionQuery` 被拒；
词表外动作在参考实现侧被拒、在宿主侧被收。⇒ 宿主按契约实现**就是错的**，
而内核参考实现与宿主对同一条留痕给出**相反结论**。⇒ 理由被写在了**错误的一侧**
（解释在私有实现的注释里，契约侧没有）（#372）。

**（e）「声明了但做不到」与「根本没声明」在本仓是同一种病，成本差一个量级。**
`statemachine.IsTerminal` 的注释承诺「词表以转移表为准」，代码不读表（#374）；
`taskboard.StateFailed` 的常量注释说「终态」，`Terminal()` 说只有 done 是（#375）。
这类缺陷当前**无运行时失效**，但它们是**下一位维护者的第一入口**——
而维护者读到的正是注释。按本仓纪律「声明与实现不符仍算缺陷」，它们独立成立。

### 这一轮新出现的五个形态（比单条缺陷更值得记住）

**（a）门禁的「负对照」自己也会有覆盖盲区。** `examples:` 机制的设计是对的
（一正一反、共用真实判定核、加载期断言），但它只要求「有正例有反例」，
**不要求覆盖正则的每个分支**。于是 `harness-single-errors-package` 的
`^github\.com/pkg/errors$` 那一半**没有任何样例** ⇒ 删掉它，`examples:` 全绿、
加载期自校验全绿、门禁全绿。⇒ **上一轮「门禁自己也要能被检查」只查到了「规则有没有执行体」，
这一轮才查到「执行体的覆盖是否完整」**——门禁的负对照也需要**按分支**覆盖，
而不是「有正有反各一条」就够。

**（b）假绿有三种形状，且都读起来像在守护。** ①断言手法在坏实现下**不可能触发**
（`append` vs 下标赋值，#387）；②断言的源对象与被测对象**类型不兼容**
（`[]StepDef` vs `[]string`，#393）；③断言的点名对象**从未出现在用例里**
（`Rows()` 用例根本没构造投影器，#388）。
共同点：**用例里出现了那个符号，不等于用例守住了那个符号的契约**。
⇒ 「断言文案点名了某个 API」是**最不可信**的信号。

**（c）词表不同步的失效方向是**双向**的。** 前几轮深拷贝的失效方向多是「更松（改穿）」；
这一轮 `reconcile` → `watchdog` 的归因词表是**更严（假红）**：
生产方 4 个取值消费方只认 2 个，被成功归因的收敛路径被判成「无归因」（#391）。
⇒ 「两份词表不一致」既可能放过非法值，也可能把**合法值**判成非法；
而后者更隐蔽 —— 它不产生非法状态，只产生噪声，于是被当成「宿主注册词表没填全」。

**（d）缺省词表会违反它自己声明的不变式。** `watchdog.Config.ClosedBy` 的注释写明
「缺省四值是所有宿主共有的收尾路径，只增不减才能避免『宿主少写一个值就把合法归因判成红』」——
而缺省四值**自己**漏了 `reconcile` 的两条（#391）。
⇒ **自述的不变式需要机判**，否则它只是**愿望**：注释里写「只增不减」的那张表，
正是最可能悄悄少一项的地方。

**（e）同一包内两个宿主接缝的 panic 口径可以相反。** `eventbus` 的 `onDrop`
走 `subhub.Do` 隔离（issue #328 已修），`Store.Insert` 在同一个发布临界区里**不隔离**；
而 `internal/subhub` 的包头不变量明写「回调 panic 不得影响发布面」（#399）。
⇒ 「这个包已经处理过 panic 隔离」这句话，**只对被显式修过的那一个接缝成立**；
同包的第二个接缝不会自动继承。

1. **「手抄」必须可机判** ⇒ 判据收窄成一句话：取值属登记表 ⇒ 出现它的那个包须

## 19. 第十轮台账（2026-11-18）：第九阶段两条建议的**字面形态**被实测驳回，改为「函数面」两条判据

### 两处「字面形态不可落地」的实测证据

1. **「枚举出口有没有人消费」不可落地**：本仓登记的 5 个枚举出口

   ⇒ 改为**「判定谓词与出口同源」**：枚举出口读同一张表只保证「表 ↔ 出口」不漂，
   而判定面（`IsKnownStatus` / `StepStatus.Valid` / `State.Valid`）是
   **另一个独立读表的地方**——它若另抄一份清单，判定与词表就分叉了，而没有任何判据会红。

2. **「在不在判定路径上」的前提不成立**：原建议要 `go/types` 档的类型信息，

   **全部**落在别的词表上（严重度 error/warn、HTTP ok）⇒ 通用判据必然成片假阳。
   ⇒ 替代落点是上面那两条「函数面」判据：它们判**声明与事实的对应**，不依赖语义推断。

### 记录：一次**环境面**挂死（根因已定位，别当成代码回归）

第十轮跑全量门禁时，`race` 步骤里先后有三组包（`steer` / `taskboard` /
`taskboard/boardtest`，第二次换成 `statemachine` / `steer`）**在启动后
零 CPU 占用**挂死超过 10 分钟；Go 自带的 10 分钟用例超时**没有触发**。

**根因（用 macOS `sample` 抓到原生栈）**：主线程停在动态链接器
`_dyld_start` —— 进程**根本没进 Go 运行时**，所以「用例超时」这个看门狗压根不存在。
触发条件是机器面负载：`race` 因必须开 cgo ⇒ 二进制**动态链接** ⇒ 启动期要在 dyld
上抢锁；当时本机 10 核、**load average 33**（多个并行会话同时在编译别的仓）⇒ 内存压力下
有进程卡死在启动期。⇒ **与代码无关**：单包重跑各 1.1~1.6 秒通过，全量 `-race` 重跑全绿。

**处置（已落地）**：给 `make race` 加**看门狗**（Makefile 的 `RACE_TIMEOUT`，
缺省 1800s）——到点杀掉 `go test` 及其子进程并**非零退出**。
理由：**「门禁挂死」是最坏的失败形态**（不产出任何结论，读日志的人会误以为「没输出 = 没跑」），
而「门禁红」至少给得出结论。macOS 没有 `timeout(1)`（coreutils 未装），
故用后台计时器自己兜一层。

记在案还有一个理由：它若出现在某次提交里，很容易被误判成「这轮改动引入的回归」。
⇒ 下次再遇到同样形态（进程在、CPU 为 0、超过用例超时仍不退出），
**先按环境面排查**（看 `sample` 的原生栈 + `uptime` 的 load），
不要先翻代码。

第十阶段列了三条建议，本轮全部处理：第 1、2 条按**实测证据**修正形态后落地，

### 建议 1 的落地形态：**前缀**而不是常量名清单

「族的键集合 ≡ 该族常量集合」这句话本身不能直接机判——「族」是哪个集合？
两种落法：

- **列出常量名**（policy 里抄一份清单）⇒ 那份清单自己就是第二份会漂的真相，
  且它漂的方向恰好是「门禁判的和代码跑的不是一套词表」——失败形态是门禁变绿。⇒ 否决。
- **声明族前缀**（`family: Status`）⇒ 主人包里名字以它开头的、取值可解析为非空
  字符串的常量就是族成员。族是**形状**声明，与 `backing` / `enum` / `predicate` 同类。

同族里常含**另一张表**的常量（`protocol` 的 `Decision*` 同时含 `decisionAll` 的 3 个
与 `decisionSources` 的 7 个）⇒ 族前缀判不出归属 ⇒ 给按前缀的豁免口
`family_exclude`（**必须写理由**），豁免**失效即红**（豁免今天什么都没豁免，却会在
将来出现同名常量时无声生效——与 exceptions 段同款纪律）。

| `protocol.confidenceAll`（high/medium/low） | 0 | **登记** |

### 建议 1 的落地：**形状不决定判不判，只决定能不能派生取值**

§20 建议 1 写的是「分组形状的判定表」——本轮**实测发现该建议的前提不成立**：
切片承载的词表有两种形态，此前被混为一谈。

| 形状 | 例子 | 含义 | 取值可派生？ |
|---|---|---|---|
| 元素是**常量名** | `[]Action{ActionForce, ActionAdjudicate}` | **扁平表**（一张表，只是写成了切片）| **可**（与 map 形状等价）|
| 元素是**复合字面量** | `[]struct{...}{{...}}` | **分组表**（一张表分成若干组）| 不可（取值在组内）|

⇒ 被挡住的 `controlplane.interventionActions` 属**前者**（它有判定面
`IsKnownInterventionAction`，其消费侧此前没人管）。拆分后它登记进来，
**实测手抄命中 0 处** ⇒ 登记不带来任何噪声。分组形状维持原判据（写
`kind: input`，判出口与归一出口同源）。

**这一轮真踩到的坑**：夹具 `[]string{wordFailed, wordOK}` 是**常量切片**，
不是分组表 ⇒ 旧用例实际测的是「常量切片被误判成分组表」这条路径，而它要的恰恰是
分组表。**夹具写错形状 ⇒ 用例测的其实是另一条路径 ⇒ 门禁的覆盖出现盲区**——
已把夹具改成真正的分组形状（元素是复合字面量）。

### 建议 2 的落地：**族 = 一个或多个前缀**

一族的常量**不一定**共享同一个前缀（`StatusXxx` 与 `PhaseXxx` 同族）。
单前缀会漏掉一族的一半 ⇒ 漏掉的那半永远没人管。

⇒ `family` 接受**字符串或列表**（单前缀是常态，列表是跨前缀时的写法）。
形态兼容是**声明面**的要求：policy 多一种写法，就少一种「宿主写不出来只能改
执行体」的风险。写错形态必须**响亮报错**——当成「没声明族」= 静默降级成
「不判反向覆盖」，而门禁照常报绿。

### 建议 3 的落地：**中心清单 + 指路按关系改口**

§20 建议 3 写的是「需要一条『同名不同义的表要显式声明互斥』的机制」。
本轮落地为**关系声明**（不是「互斥」而是「同 / 不同」两档）：

| 关系 | 含义 | 手抄指路 |
|---|---|---|
| `same` | 同一概念（一张表的别名/子集）| 列出全部候选常量（引用任一家都对）|
| `distinct` | 不同概念（同形只是拼写巧合）| **在本包另起一个名字**（引用任一家都可能是语义损坏）|

为什么不用「互斥」一档：两张表**可以**是同一概念（statemachine 的环节状态常量就是
contract 会话状态的别名），一刀切「互斥」会把别名关系判成错。

为什么用**中心清单**（`relations`）而不是各表自己声明：关系是**两张表之间**的事，
写在任一方都会引出「两边都声明了但不一致」的第三种状态。

**失败形态全是变红**：撞车没声明 ⇒ 红（没人说得清这处字面量想说的是哪张表）；
声明了没撞车 ⇒ 红（**声明失真**：今天没关系，将来一旦同形就会无声生效）；
关系值域不封闭 ⇒ 红（写错的关系名会被落进「不同概念」那一档 ⇒ 指路语义损坏）。

### 建议 1 的落地：**关系锚到常量，于是「说谎的关系」当天即红**

§21 建议 1 的原文是「关系声明能引用**具体常量**（至少 `same` 关系要），让『常量改名/
常量被删』当天即红」。本轮落地为 `relations[].anchors` 段，四条判据：

| # | 判据 | 拦的是 |
|---|---|---|
| 1 | 锚点常量必须**存在**且取值可解析 | 常量**改名 / 被删**（= 登记漂移）|
| 2 | 锚点常量的取值必须**属于它那一端的表** | 锚点说的是**别的表**的词 |
| 3 | 两端锚定的取值必须**成对** | 关系的前提「同形」不成立了（两端漂开）|
| 4 | `distinct` 的两端锚点必须解析到**不同处声明** | 「不同概念」是**说谎**的 |

判据 4 的机器依据是**别名链的根声明**：`statemachine.StatusFailed = contract.StatusFailed` ⇒
两端锚点解析到**同一处声明** ⇒「同一概念」是**证过**的事实，不是人说的；反过来，
`distinct` 若两端锚到同一处声明，同一处声明就不可能是两个概念 ⇒ 那条声明在
说谎 ⇒ 手抄指路会要求本包另起名字，而正确做法是引用主人常量。

### 两处**故意不对称**的设计（别当成疏漏）

1. **`same` 不要求根声明相同**：两张表**各自独立**定义同一个词形且含义相同，
   也是合法的 `same`（机器判不了语义）⇒ 强制要求根声明相同会把那种表逼成假红
   ——**门禁逼人造假比没有锚点更坏**。`same` 只受判据 1~3（取值漂了、锚点烂了仍会红）。
2. **锚点是可选的**：键是字面量、根本没有常量可锚的表**写不出**锚点 ⇒ 不强制。
   但**半边锚点没有配对语义** ⇒ 要写就两端都写（自校验当天即红）。

### 建议 1 的落地：all 形态（锚住两端共有取值的全集）

  （判据 3）；`distinct` 的**每一个**共有取值都要解析到不同处声明（判据 4）。
- **覆盖面差别可数**（同一句谎话：把一条 `distinct` 关系指向同源的两张表）：
  - 抽样形态：报 **1** 条（只验了被抽中的那个取值）；
  - all 形态：报 **12** 条（每个共有取值各一条：approved / cancelled / created /
    expired / failed / interrupted / …）。
- **为什么形态是 `[{all: true}]` 而不是台账草稿里的 `a: all`**：锚点列表是**导出
  字段**（`[]WordTableAnchor`），支持标量就得换成自定义 UnmarshalYAML 的新类型 ⇒
  宿主构造该结构的代码会编译不过（拿破坏性变更换两个字符的写法，不划算）。

### 建议 2 的结论：「有没有名字」这条洞**不成立**（核验 + 写明边界）

- 台账担心的「名字放在一个根本没人读的包里」：现判据**不会**放行——手抄判据是
  **出现点级**的（字面量必须**就是**本包某个常量声明的值），同包别处再写同一个字面量
  照样判红（`TestWordTableLiteralAfterOwnConstantIsRed` 钉着）。
- 「在不在判定路径上」这条更强的判据：§19 已**实测驳回**（类型不携带语义 + 拼写撞车
  是常态 ⇒ 通用判据必然成片假阳）。
- ⇒ 本轮**不加** go/types 判据，只把边界写明（免得下轮重复提出）。**不新增判据也是
  收口**——把「为什么不加」写清楚，比加一条会误报的判据更有价值。

### 建议 3 的落地：族归属由表自己声明（`family_exclude` 废弃）

- 每张表声明自己**拥有**的常量名前缀（`family`）；一个常量归哪张表按**最长匹配
  前缀**决定（同包里更具体的前缀赢，与 http mux 同一思路：前缀之间有包含关系时，
  唯一自洽的规则就是「更具体的那个拥有它」）。
- **未登记但声明了归属**的表也算归属方（`not_registered` 段的 `pkg` + `prefixes`）
  ——不登记 ≠ 没人管：那段常量仍会被同包另一张表的族前缀命中，不声明归属就会被算成
  「漏进表」（假红）。
- 本仓三处手写豁免（`ConfidenceKind` / `DecisionSource` / `ActionQuery`）全部删掉，
  改由归属声明表达。
- `family_exclude` **废弃**：仍写 ⇒ 自校验当天即红，并写明怎么改。字段**保留**（直接
  删字段会让宿主 policy **静默**失效——yaml 忽略未知字段 ⇒ 保留字段 + 报红才是
  「响亮地要求迁移」）。

### 反向验证（7 条新变异全部打红，累计 30 条）

新增 7 条：all 形态不再判「本端缺常量」/ all 形态把非共有取值也算进来 / distinct 的
同源检查在 all 形态下失效 / 归属派生退回「先声明者赢」/ 归属派生整体失效 / 自校验的
前缀冲突检查失效 / 自校验的 family_exclude 废弃提示失效。脚本先断言「变异落地」再读
测试结果，断言落在**判据**上。

**本轮踩到的两个自伤**（记下来，别再踩）：

1. **用例不承重**：M1 变异（「缺常量」检查失效）最初报 WEAK——因为「本端没有常量」与
   「常量解析不出」报**同一个 kind**，判据坏掉也看不出 ⇒ 修法是给两种事实**分开 kind**
   （`word_table_anchor_no_constant` vs `word_table_anchor_missing`）：报告要能区分
   「**哪种**事实没成立」，否则报红也指不准路。
2. **变异打歪**：M7 的锚点 `for _, ex := range t.FamilyExclude {` 在文件里出现**两次**
   （缺理由检查 + 废弃提示），`replace(…, 1)` 命中的是**前一个** ⇒ 改的不是要验的那条
   ⇒ 报 WEAK。修法：锚点要带**消息文本**，唯一到那一条。

### 负对照（policy 层面的实机验证）

把一条 `distinct` 关系指向同源的两张表（contract ↔ statemachine）⇒ 真门禁当场报
**14 处**阻断级违反（12 处锚点同源 + 1 处撞车未声明 + 1 处），还原即绿 ⇒ 判据**真的在
判**，不是照常报绿却什么都没判。

### 建议 1 的落地形态：**单号 → 状态由台账自己声明**，门禁只读派生结果

§15 形态 (a) 的代价是整条工作树作废：一批单**早已由 8 个 PR 合入主干**，而接手的人

本轮把它做成三件事：

1. **派生器下沉为可导入包**（`internal/ledgerstatus`）：台账是 markdown 散文，机器
   只能靠三处约定——登记列（表头为 单号 / 单 / 已落单 / 结论单）、状态列（表头为
   状态）、散文标记（正文行里的「已合入」「仍开着」）。三处约定写在包头，解析

   不是一套」。
3. **PR 号不进单号视图**：落文档 PR #281、合并 PR #339 / #340 是 PR 号，进视图
   就等于把两种号混成一种（同一个号在一处是关闭 PR、在另一处是单号）。

### 顺带修掉的一处 CI 缺口：两条门禁在 CI 上**从来没跑过**

接新门禁进 `make check` 的时候顺手核了一遍「CI 到底执行什么」，发现：
CI 的七个作业执行的是**分层目标**（`unit` / `race` / `contract` /
`fault-injection` / `gates` / `integration`），**没有任何一个执行 `make check`
本身** ⇒ 只挂在 `check` 上、没进任何分层目标的门禁，CI 上一次都不会跑。

实测被漏掉的是两条：**`deploycheck`**（部署清单门禁，issue #277）与
**`releasecheck`**（发版纪律门禁）——它们一直只挂在 `check` 上。后果：
矩阵漂了 CI 不会知道；tag 推送时那四条发版纪律（annotated tag / CHANGELOG 含
本版段 / 无编码损坏 / 区间无混装提交）也**没人判**。

⇒ 修法：三条（`deploycheck` / `ledgercheck` / `releasecheck`）接进 `unit` 层，
**不改编排目标的层次结构**——job 名一改，分支保护的 required contexts 就对不上，
PR 会永远卡 BLOCKED（改名的同步成本见 `docs/AI-GUIDE.md` §4 的 job 名纪律）。
另外给 unit 层的 checkout 加 `fetch-depth: 0`：`releasecheck` 的「区间内混装
提交」判定要读**上一个 tag**，浅克隆里没有父提交历史 ⇒ 那条判定只能显式跳过
⇒ tag 推送时只判三条。501 个提交 / 51M 历史，代价可忽略。

⇒ **纪律**：门禁接进 `check` 之后还要问一句「**CI 跑的那个分层目标里有没有它**」。
判据本体仍写在 `check` 里（本地一条命令跑全），分层目标负责**让 CI 也判**。

### 本轮的两个自伤（都是「夹具不承重」与「脚本锚点被吃掉」）

1. **「状态列空 ⇒ 仍开着」这条分支原本没有承重夹具**：合成台账里那一行的状态列
   虽然是空的，但**同一行还有一条散文标记**（「仍开着」）⇒ 派生结果来自散文，
   不是来自空单元格。变异「空单元格不再算仍开着」打过去，用例照样全绿。
   ⇒ 处置：补 `TestEmptyStatusCellMeansOpen`（只有空单元格、没有散文标记），
   变异随即转红。**教训**：夹具里两条路径同时命中时，第二条路径就是隐形的。
2. **变异脚本的锚点被 Python 词法器吃掉半个引号**：锚点写成三引号串且以引号结尾
   （`return ""`）⇒ 词法器把 `""` 当成结束符的一部分，锚点悄悄少了两字符 ⇒
   变异「落地」了却编译失败（脚本按纪律报 BUILD，不计红）。
   ⇒ 处置：锚点一律改用单引号串 + 逐行拼接（`L(...)`）。**教训**：写变异脚本时，
   「锚点没落地」与「锚点落地了但变形了」是两种不同的坑，后者更贵——它会伪装成
   「判据没抓住这个坏实现」。

### 下一阶段（第十六阶段）建议

1. **「台账自己」也要能被门禁判它自己的纪律**：本轮的门禁判的是台账的**内部一致性**

   仍然是**两处真相**——台账写「已合入」而 GitHub 上那条单还开着（或反过来），
   机器现在看不出来。判据要联网就意味着 CI 必须有凭据，得先想清楚**断网时怎么办**
   （大概率是「断网即跳过并明确说跳过」，不能静默当绿）。
2. **矩阵的「能力没主」要能反查**：本轮给两条真缺口开了新单（#418 / #419），但
   「每条缺口都挂着仍开着的单号」这条只做到了**声明面自洽**——没人查**反过来**
   「还开着的单有没有对应到矩阵里的一条能力」。反向检查需要一个从单号到能力的
   登记面，否则「开了单却没人认领」这件事只能靠人扫。
3. **词表登记面与本轮的两套登记面要合并读**：判定词表登记（`word_tables` 段）与
   单号登记（台账 §9 / §9.1）是同一类机制的两个实例——「取值/单号出现在别处时，
   主人表自己声明」。两者的**声明形状**已经同构（中心清单 + 逐条派生），但**执行体**
   仍是两套代码；合并前要确认两边的派生口径（交集 vs 并集）能对齐，否则合并只会
   把两套漂移叠成一套。

## 25. 第十六轮台账（2026-11-18）：#419 清偿——单一存储覆盖全部状态（四个面共用一份事务域）

### 落点

- `examples/sqlitestore/`（PR #421）：四个面共用一份事务域。
- 部署清单能力 `single-store-full-state`：partial → **available**（`delivered_by: "#419"`）。
- 部署场景 `single-host-persistent`：partial → **available**。

### #419 补的不是「一个包」，是**跨面原子性**

#188 交付的是任务板侧的单机落库（能力条目的措辞是「任务板之外还含副作用 /
事件 / 快照」）。#419 若按「再补三个包」做，交付的仍是四份**互不相干**的落库：
四个面各自能落库 ≠ 一份存储能覆盖全部状态。

真正的差口是**跨面变更能不能落在同一次提交里**：

- 任务板说「这一步做完了」，事件面要同时留下一条事件行（Outbox）：分两次提交
  ⇒ 崩在中间 ⇒「事情做完了但没留痕」或「留痕了但没做完」；
- 副作用闸说「这个动作已生效」，快照面要同时推进进度：分两次提交 ⇒ 恢复点与
  事实对不上 ⇒ 重启后重复施加。

⇒ 落库形态的做法：日志升级为**「一行 = 一个事务批次」**。跨面的变更在磁盘上
是**同一条记录** ⇒ 要么整批可见，要么整批不可见 ⇒ 跨面不会出现「一半已提交」。
（v1 旧格式「一行 = 一条任务记录」仍可读，旧目录不必迁移；旧记录读进来后与新
记录走**同一条应用路径** ⇒ 只有一份「记录怎么变成状态」的算法。）

### 事件游标：从「已提交水位线」派生，而不是自增序列

事件 ID = 已提交水位线 + 1；水位线只随**提交**推进，回滚既不推它也不烧号
（下一个事务重新从同一点派生）⇒ 铸造序 == 提交序 ⇒ **序列空洞结构性地不存在**
⇒ `eventbus.TailStore` 的「无空洞推进」硬要求由**构造**满足，而不是靠「读的
时候小心别跳过」这种约定。

日志层另有一条连续性判据：事件 ID 出现空洞 ⇒ 响亮失败（静默跳过会让尾随读侧
永久跳过那个 ID——丢帧且无告警）。

这同时把本存储**声明**为 Outbox 形态（实现 `WatermarkTailStore`）——那是
`eventbus` 契约点名的**唯一被承诺支持的生产形态**；「自增/序列 ID 直读」显式
不支持（乱序提交丢帧 + 回滚烧号停摆，两类丢失都不在调用方可修）。

### 本轮的两个自伤（都是「同一个判断写了两份」）

1. **三项联查在两个入口各写一遍**：资源闸与执行意图各自比一次「持有者身份」
   与「令牌代次」——**判的是同一件事，却有两份代码**。变异打掉其中一份，测试
   **照样全绿**（另一份还在判）⇒ 那条判据事实上**没有承重夹具**。
   ⇒ 处置：三条联查各收成**唯一判据点**（`effectHolderErr` / `effectFenceErr` /
   `effectResourceErr`），两个入口都调它。**教训**：同一件事只由一个主人判；
   判据写两份 ⇒ 变异看不见差异 ⇒「有测试」是假象。
2. **提交闸也有两份**：事务失败既在 `stage` 里被拒、又在提交前被查 ⇒ 变异打掉
   其中一处，另一处照样拦住 ⇒ 同样看不见差异。

⇒ **教训（比上面两条更一般）**：变异脚本的价值不只在于「抓坏实现」，也在于
**抓自己的判据没有承重**——「改坏一处，测试全绿」这件事本身就是要报的结论。
本轮 14 条变异里 2 条打红的是自伤，其余 12 条打红的是既有判据。

### 要解决的真问题：红的形态得靠人猜

race 门禁此前只回答「绿 / 红」。红的**形态**要靠人读日志推断，而不同形态的处置
方向完全相反（改代码 vs 查机器面）。2026-11-18 实录的一次误归因就是这个缺口的
账单：

- 现象：`FAIL github.com/yi-nology/goagent-kernel/statemachine 660.101s` +
  `*** Test killed with quit: ran too long (11m0s).` + `signal: quit`，**一行
  goroutine 栈都没有**。
- 当时的归因：「statemachine 的用例挂死了」。
- 事实核验：那个包零计时敏感点（无 `time.*`、无 goroutine/channel、无
  `os/exec`）⇒ **它的用例根本没有能挂住的东西**；真因是 race 二进制卡在 macOS
  动态链接器**启动期**（Go 运行时压根没起来 ⇒ 连 Go 自带的用例超时都不触发）。
- 后果：归因错了 ⇒ 处置必然错 ⇒ 在一个**零缺陷**的包里查代码。

⇒ 本轮把「形态判定」从人的脑内活动变成**机器判定**：`cmd/raceprobe` 把失败分成
六种形态并各自给出处置，落取证。

### 三条可复用的判据（比「怎么修这个 bug」更值钱）

1. **症状不是判据，机制指纹才是。** 「超时了」是症状（两种形态都超时）；
   「**有没有 goroutine 栈**」是机制指纹（能留下栈 ⇒ 运行时活到过 ⇒ 用例问题；
   留不下 ⇒ 运行时压根没起 ⇒ 环境问题）。同理，`*** Test killed with quit: ran too
   long (11m0s).` 是 cmd/go 的兜底闹钟（`testKillTimeout = testTimeout + 1m`）——
   它出现**且没有栈**，才是楔死的指纹。
2. **判据要判的那个形态若不可复现，判据就必须能脱离复现被钉死。** 本机无法稳定
   复现 11m0s 楔死 ⇒ 形态判定做成**纯函数**（输入一段输出文本，输出一个结论），
   用构造出来的文本逐条钉住（含反向验证：栈与兜底闹钟同时出现时必须按证据强度取
   最硬的那个）。**判据跑不到 ⇒ 改坏了没人知道 ⇒ 门禁是看着在、其实没判。**
3. **环境面失败也要给机器结论，否则每次都要人重做一遍归因。** 形态是
   `startup-wedge` 时做**反事实实验**：同树、`-p 1`（拿掉「并行启动」这个变量）
   重跑受害包 ⇒ 复核通过 ⇒ 判「环境面已复核」；复核失败 ⇒ 按复核结论判红。
   这个方法与人工定责同源（换一个变量重跑一次对照），差别只在于**每次都执行**。

### 三段预算互相咬合（改一处必须改三处）

`RACE_GO_TIMEOUT`（`go test -timeout`）→ cmd/go 兜底闹钟 = 它 + 1m →
`RACE_WATCHDOG`（本工具的看门狗）**必须晚于兜底闹钟**。早了就变成我们先杀
`go test` ⇒ 拿不到那行指纹 ⇒ 判定退化成 `unknown` ⇒ **取证能力自己把自己废了**。
工具自己会拒这种配置（退出码 2），而不是默默降级。

### 下一阶段（第十八阶段）建议

1. **形态判定应当可复用**：`cmd/raceprobe` 的判定层现在是 `package main`，别的
   门禁（fault-injection / integration 也可能撞上「会挂死」的形态）用不了。
   建议按 `archcheck` 下沉的同款纪律，把它下沉为**可导入包**（判定面与执行面分离，
   宿主与别的门禁复用同一份判据）——本仓的老教训：**机制面若要跨仓复用，就不能锁在
   `package main` 里**。
2. **「会挂死」的门禁要统一形态**：`make fault-injection` / `make integration` 的
   失败形态目前也靠人读日志。可判的形态是：各门禁失败时都落一份**同构**的取证
   （原始输出 + 形态结论），形态分类共用一套判据。
3. **§25 的两条建议仍未处理**（单机落库的 DDL / 事务脚本形态化；「单机」边界可判化），
   按原顺序排在后续轮次。

### 先修掉一个**会让结论不成立**的用例缺陷（假绿）

原用例把探测目标写成 `https://kubernetes.default.svc/healthz`，探针脚本是
`if wget …; then …; else …; fi`，而 busybox wget **不支持 HTTPS**（alpine 的 busybox
未编 TLS）⇒「wget 失败」既可能是被 NetworkPolicy 拦下，也可能是 wget 压根不会说
HTTPS ⇒ **禁网没生效时用例照样绿**。

本版把判据改成**有阳性对照**的形态：同一台集群、**同一条**探针脚本、**同一个**目标，
唯一的变量是那张 NetworkPolicy：

| 侧 | 策略 | 断言 |
|---|---|---|
| 对照 Pod | 无 | 必须连上：退出码 1（探针约定「连上 ⇒ 失败」）+ 打印 EGRESS_OPEN |
| 禁网作业 | 有（Egress 全拒） | 必须连不上：退出码 0（= `probe_exit_0`）+ 打印 EGRESS_BLOCKED |

两个方向都断言 ⇒「绿灯」不再可能由「探针压根不通」冒充。

目标用**集群内见证端点的数字 IP**（而不是域名）：域名解析本身也是出站，被拦时失败落在
DNS 层 ⇒「连不上」与「解析不了」分不开。

⇒ 这条修复的收益不止于本单：**任何「数据面行为」的验收，只要断言的是「某个连接失败」，
就必须同时断言「同一个连接在无策略时能成功」**，否则失败原因不可区分。

### 本轮实测的三条关键事实

1. **存储时钟是毫秒级**：存储时钟走 `unixepoch('subsec')`，但**消费面按整毫秒截断**
   （`CAST(unixepoch('subsec') * 1000 AS INTEGER)`，`examples/sqliteadapter/exec.go:145`）
   ⇒ **有效分辨率恰为 1 ms**（实测相邻差值只有 0/1 ms）；引擎原始 `unixepoch('subsec')`
   的最小正增量约 **0.9999 ms**（截断前的原始粒度，≈1 ms）⇒ 比 PG 的
   `clock_timestamp()` 微秒级粗 ⇒ **租约 TTL 建议 ≥ 1s**
   （`examples/sqliteadapter/doc.go:65`）。亚秒 TTL 的过期判定边界不可预期。
2. **事件 ID 无空洞**：无空洞推进是 `eventbus/tail.go:87` 的**硬要求**
   （issue #183 / #264 收口）；`examples/sqliteadapter/event.go:19` 声明它
   **由机制保证**（水位行锁串行化 + 回滚不烧号），不靠约定、也不靠观测截断。
3. **水位线 ≠ 事件表 MAX(id)**：`examples/sqliteadapter/event.go:33-39` ⇒
   水位线读**水位行**、`MAX(id)` 读**事件行**，上界关系是「**水位线 ≤ MAX(id)**」；
   `MaxID` 与 `CommittedWatermark` **同值同源**（都读水位行），**不回裸 `max(id)`**。

### 选型口径：三条 + 一条硬边界

（权威出处：`docs/STORAGE-SELECTION.yaml` 的 `policy.notes` 与 `docs/USAGE.md` §3.17；
门禁 `make storagecheck` 逐条判，不靠本文转述。）

1. 需要**跨进程 / 跨机共享写**（多副本、多机、K8s）⇒ **PostgreSQL**；
2. 需要**重启后恢复**且不引入外部服务进程 ⇒ **SQLite**；
3. 只要**进程内判据正确**、不要持久化 ⇒ **memory**。

**硬边界：单机多进程一律判 PostgreSQL。** SQLite 的单写者模型在多写者下退化为串行，
`busy_timeout` 到点即失败（可判、不静默丢写，但可用性下降）⇒ 同机多进程（两个
Worker 进程抢同一份任务板）**必须**用 PostgreSQL。

⇒ 这条边界**不靠 capability 归属碰巧撑着**（归属一旦被人改错，硬边界会跟着失效）：
门禁按两张**数据**表判——`scenario_writers`（场景形态 → 并发写者数）与
`max_writers`（存储 → 写者上限）⇒ 多写者场景选了单写者档位**当场红**。

### 本轮新增的机器判据（判什么 / 失败形态）

1. **`harness-test-goroutine-joined`**（`severity: error`，`only_test: true`）：
   触发 = 测试函数里有 `go` 语句；豁免 = 函数体内或其调用的**包内函数**（深度 ≤2）里有等待点
   （`<-ch` 或 `X.Wait()`）。失败形态 = 红，且**点名**文件:行 / 测试函数名 / goroutine 形态 / 原因。
   ⚠ 豁免**必须 helper 感知**：等待点常常写在助手（`stopTailer`）里 ⇒ 只看测试函数体 ⇒ 大量误报
   ⇒ 误报把真阳性淹没。⚠ **等待点不看 goroutine 自己的函数体**（那是在等别人，不是测试侧在等它）。
2. **`check_kind` 字段 + 封闭取值域**（架构面）：policy 的规则此前只有两种执行体
   （`forbid_regex` 判源码文本 / `forbid_import_regex` 判 import 路径），而这条纪律判的是**结构关系**
   ⇒ 新增第三种形态。**取值域必须封闭**：写错的类别名若被当成「不是已知类别」，这条登记就
   **静默降级**成「不判」——规则在、severity 是 error、报告里照常计入条数，只是永不触发 ⇒
   **失败形态是门禁变绿** ⇒ 未知取值当天即红。
3. **结构化样例走同一个判定核**：policy 的 `examples:` 与真判定共用 `gjJudgeFiles` ⇒ 样例过了
   才说明真判定也过（两套实现各自漂移，样例那套只看几个字符串、漂得更慢 ⇒ 绿灯更久，
   正是「从见过它触发的规则等于没有规则」最隐蔽的形态）。

### 本轮仍然存在的边界（如实登记未被机判的断言）

1. **这条规则是静态形状判据，不是运行时保证**——四条照不到的形态（已写进 `archcheck/testgoroutine.go`
   的文件头）：① **任意接收表达式都算等待点**（`<-time.After(...)` 也算）⇒ 假阴性；
   ② **豁免粒度是「用例级」而非「goroutine 级」**（一个用例有一处等待点 ⇒ 该用例内所有 goroutine
   一起豁免，含那个没被等的）；③ **`X.Wait()` 匹配任意选择器调用**，与被启动的 goroutine 是否相关
   **不校验**；④ **等待点写成「用例末尾的普通语句」而非 `defer`** ⇒ 用例中途 `t.Fatalf` 触发 Goexit 时
   那一步**不执行** ⇒ goroutine 实际未被 join，而规则**判它合规**。
   ⇒ 与本仓既有纪律「门禁绿 ≠ 机制成立」同族；第 ④ 条已开 **#431**。
2. **v0.51.0 那 9 处收尾点仍是「用例末尾的普通语句」** ⇒ 失败路径仍会漏（**#431**）。
   ⚠ 且**不能一刀切 defer**：其中 **2 处是用例中途**的收尾（第一程收尾，后面还有「停机窗口」
   第二程）⇒ defer 会把第一程的 tailer 拖到用例结束才 join ⇒ **语义改变**。
3. **`worker` 的 `TestManagedExecutorRenewalPreventsTakeover` 靠时序撞窗口**（**#430**）

### #431｜用例里的收尾点必须是 `defer` 形态（9 处）

**问题**：v0.51.0 那 9 处尾随收尾点写成「用例末尾的普通语句」。`runtime.Goexit`
（用例体里 `t.Fatalf` 触发）执行**所有 defer**，但**不执行**它之后的普通语句
⇒ **失败路径上那一跳根本不执行** ⇒ tailer 实际未被 join，而用例已判失败
（`archcheck` 那条规则判的是静态形状 ⇒ 判它合规）。

| 位置 | 原形态 | 现形态 |
|---|---|---|
| `examples/sqliteadapter/cursor_tail_test.go` 第一程 | 用例体**中途**的普通语句 | **闭包内** `defer`（本程结束即收尾） |
| 同文件 第二程 / 重读续随 | 用例末尾普通语句 | `defer stopTailer(...)` |
| `examples/sqliteadapter/cursor_fail_test.go` | 用例末尾普通语句 | `defer stopTailer(...)` |
| `examples/sqliteadapter/event_tail_test.go` | 用例末尾普通语句 | `defer stopTailer(...)` |
| `examples/pgstore/pg_cursor_test.go` 第一程 | 用例体**中途**的普通语句 | **闭包内** `defer`（本程结束即收尾） |
| 同文件 第二程 / 重读续随 | 用例末尾普通语句 | `defer stopTailer(...)` |
| `examples/pgstore/pg_event_test.go` | 用例末尾普通语句 | `defer stopTailer(...)` |

⇒ **7 处末尾 + 2 处中途 = 9**。中途收尾**不能一刀切 defer**：第一程的 tailer 必须
在「停机窗口」开始**之前**退出（否则它会吃掉停机窗口里发布的事件，第二程补不到
4..5）⇒ defer 若写在用例体末尾，join 被拖到整个用例结束 ⇒ **语义改变**。
正解是**把那一段圈成闭包、defer 写在闭包里**：收尾在本段结束时发生（语义不变），
失败路径上仍然 join（Goexit 执行所有 defer）。

**失败路径实测仍 join**：新增 `TestDeferredTailerCleanupJoinsOnGoexitPath`——在一个
goroutine 里注册 defer 后调用 `runtime.Goexit()`，断言该 defer **真的等到了**
goroutine 退出（标志法：确定性，不靠 sleep 概率）。
**反向验证**：把判定核改成「只取消、不等」⇒ 新用例与既有的
`TestStopTailerWaitsForGoroutineExit` **同时红**；撤销后复绿。

**另两条实测（供照抄）**：① defer 里的 `t.Fatalf` 在 Goexit 失败路径上**安全**
（不会挡住更早注册的 defer，也不触发嵌套退出）⇒ 收尾助手不必换掉 Fatalf 语义；
② **判定核与断言可以分开**（收尾助手返回一个 bool、断言交给调用方）⇒ 失败路径上的
收尾能在**任何 goroutine** 里执行。

### #432｜断言的尺子必须是可观测事实（8 处同形面）

**问题**：固定 `time.Sleep(d)` 之后再断言计数 ⇒ 墙钟窗口与被测机制的真实节奏**无关**
——机器一忙，窗口里就可能什么都没发生。两种失效形态：**窗口落空 ⇒ 假红** /
**证据落空 ⇒ 白测**。全仓 8 处已逐条判定（A 类 1 / B 类 3 / C 类 4）并改造，
**每一处都带「坏实现会红」的实跑证据**。

| # | 位置 | 类别 | 现形态（尺子 = 可观测事实） | 反向验证（坏实现 ⇒ 红） |
|---|---|---|---|---|
| S1 | `worker/lease_callback_test.go` | **A（已实测红）** | 有界等「**第 3 次续期真的发生**」（5s 上限 / 1ms 轮询） | 去掉 panic 隔离 ⇒ 「心跳必须在 5s 内续期到 4 次（实得 1）」红 |
| S2 | `pii/policy_atomic_test.go` | **B（窗口落空假红）** | 在并发读写**还在跑**时有界等 `torn > 0`（5s 上限） | 读侧永不撕裂 ⇒ 「对照组失效：5s 内一次撕裂都没读到」红 |
| S3 | `netguard/subscribe_edge_test.go` | **B** | 有界等「**变更通知到了 50 次**」（5s 上限 / 1ms 轮询） | 跳过通知 ⇒ 「5s 内收到的变更通知不足 50 次（实得 0）」红 |
| S4 | `pii/subscribe_edge_test.go` | **B** | 同上 | 同上 |
| S5 | `eventbus/tail_cursorstore_test.go` | **C（证据落空白测）** | 有界等「**停摆持续了 8 拍**」（Load 尝试 8 次且 8 次失败） | 停摆从未发生 / 生产面回退 MaxID ⇒ 红 |
| S6 | `eventbus/tail_test.go` | **C** | 尺子换成「**读数不再增长**」（轮询 1ms×30 次、跨度 > 2×节拍） | Run 把循环挪进后台且脱离 ctx 取消 ⇒ 「Run 返回后仍在读存储（泄漏）: 0 → 1」红 |
| S7 | `watchdog/turn_test.go` | **C** | 删掉窗口、Run 返回即断言，**如实标注该断言当前恒真**（清扫只在内联路径上发生） | 给 Run 加停机扫尾 ⇒ 「停机退出不应把未闭合轮当泄漏: [turn_open_leak]」红 |
| S8 | `cmd/raceprobe/proc_unix_test.go` | **C** | 后台子进程启动即 touch marker ⇒ 有界等 **marker 出现**（10s 上限）再 `killTree` | 后台不起 / 只杀直接子进程 ⇒ 两处都红 |

**S3 / S4 的两处配套**：① 先 `resident.reset()` 掉**注册时的初始回调**（那是「现在
生效的是什么」，不是变更通知；留着它「等到 N 次」恒真）；② 等 **50 次**而不是 1 次
——本用例要验的是「名单在剧烈增删下仍能被稳定遍历」，**增删侧必须与通知重叠**才有
意义。**S8 的进程组前提**用临时探针实查过：外层 `sh` 为组长，两个 `sleep` 的 PGID
**都等于**它，`killTree` 后 `kill(-pgid,0)` 返回 ESRCH ⇒ 与改前同形。

**两处偏离原处方（均带证据，照实登记）**：

1. **S5 补了「覆盖拍数」**：按「等 Load 被读过 1 次」写完后，反向验证打脸——把夹具
   改成 Load 成功（停摆从未发生）时**用例仍然绿**（断言落在第 1 拍之后，后续拍里回退
   MaxID / 读存量抓不到）⇒ 改成「停摆持续 8 拍」后该坏实现转红。原 80ms 窗口约等于
   8 拍（节拍 10ms）⇒ 新判据盖的是**同一块地面**，但按**事实**计量、负载越重覆盖力
   只增不减。
2. **S6 没有按「立刻断言」交付**：按字面写法做出来后，反向验证显示**抓不住它声称要
   拦的坏实现**（后台读排在 10ms 节拍上，落不进那个窗口）⇒ **守卫抓不住 = 没有判据**
   ⇒ 改成「读数不再增长」这一可观测事实后转红。

⇒ 这两条正是「反向验证用例必须断言『注入的那一条被看见了』」那条纪律的用处：
**坏实现会红**不是形式，是判据强度的下限。

### #440｜「用例里的收尾点必须是 `defer` 形态」变成门禁判定

**新增规则 `harness-test-defer-cleanup`**（`check_kind: defer_cleanup`，`severity: error`，
`only_test: true`）——它关掉兄弟规则 `harness-test-goroutine-joined` 的**已登记边界第 4 条**：
那条规则判的是「测试侧**有没有**等待点」，判不出「那个等待点**会不会被 Goexit 跳过**」
⇒ 失败路径上 goroutine 实际未被 join，而规则判它合规。

**判定口径**：只扫测试文件、只判测试函数（`Test*` / `Benchmark*` / `Fuzz*`）；等待点 =
接收表达式 `<-ch` 或调用 `X.Wait()`（**跳过 go 语句自身的函数字面量**——那是 goroutine
在等别人）；等待点在测试函数体的 `defer` 内、或在**由 `defer` 调用的包内助手**里
（深度 ≤2）⇒ 合规；等待点在**普通语句**里 ⇒ 从该 `go` 语句到它之间**没有** `t.Fatal` /
`t.Fatalf` / `t.FailNow` / `t.Skip` / `t.Skipf` / `runtime.Goexit` 的直接调用 ⇒
**同步等待**（合规：goroutine 一定在用例继续之前结束）；**有** ⇒ **收尾等待**（违规）。

**新增「执行上下文」作用域模型**（`archcheck/testscope.go`）：`t.Run` 子用例闭包跑在
**另一个 goroutine** 里 ⇒ 它的 `t.Fatal` 终止的是**子用例**、不是父用例（不区分就会把
「子用例失败」误当成「父用例被提前终止」⇒ 假红）；T 绑定的归属与词法父作用域**分开记**。

**同形面清点与处置**：初始命中 **12 处**（9 个包）⇒ 9 处机械可改的直接改
（`coord` / `drain` / `examples` / `netguard` / `ptc` / `watchdog` / `worker`），
其余登记例外。**反向验证**：注入一处违规 ⇒ 门禁**红**且**点名注入的那一条**
（文件:行、用例名、等待点形态、以及那个「能让用例提前终止的调用」的行列）⇒ 撤销后复绿。

### #441｜「断言的尺子必须是可观测事实」变成门禁判定

**新增规则 `harness-test-wallclock-ruler`**（`check_kind: wallclock_ruler`）——测试面
不许拿裸 `time.Sleep` 当尺子：固定睡一段再断言 ⇒ 窗口长度单独决定结论（机器一忙 ⇒
假红；被测机制抢跑 ⇒ 白测）。

**判定口径**：测试函数体里的 `time.Sleep` 且**不在 for/range 循环体内** ⇒ 违规；
**显式登记的边界**：① **轮询退避**（sleep 落在循环体内）不是尺子——退出条件是循环
条件本身，不是窗口长度；② **goroutine 体里**的 sleep 是**被测机制自己的节奏**，不判；
③ **受管辅助**（policy 侧 `managed_helpers:` 登记）函数体内部的 sleep 不判——
声明必须在 **policy 侧**（`archcheck` 是跨宿主复用的库，硬编码辅助名单等于把宿主的事
写进内核 ⇒「登记了一张表却没生效」是最贵的静默失效之一）。

**同形面清点与处置**：初始命中 **9 处** ⇒ 4 处改成「等可观测事实」
（`drain` / `netguard` / `watchdog` / `worker`——其中 `drain` 那处**原本一直在白测**：
窗口 50ms 而收敛轮询间隔 200ms ⇒ 窗口落空，用例覆盖的其实是「入口即 Done」分支）；
2 处登记为受管辅助（`examples/pgstore` 的子进程剧本助手）；2 处登记例外。

### #442｜`pii` 包全局态还原收进一个包级 helper（**真缺陷**）

**根因（三层，缺一层都解释不了那个现象）**：① 包内**两套相反**的还原约定
（`surface_failclosed_test.go` / `mapkeys_test.go` 还原成 `SetEnabled(false)`，
而 `policy_accessor_test.go` 还原成 `true`；缺省值是 **enabled = true**，
secure by default）；② 那个 `restore(t)` helper **只在 cleanup 里还原、用例开始时
并不重置** ⇒ 下一个用例**起跑在脏状态上**；③ 还原动作在 **goroutine 里**跑且
**超时后不报错** ⇒ 还原可能落在下一个用例开始之后（跨用例串扰）。

⇒ `TestApplyHonorsStrategy` 起跑时全局 `enabled` 是上一个用例遗留的 false ⇒
`Apply` 原样透传 ⇒ 「mask 应保长打码，实得 13800001234」。

**修法**：**一个**包级 helper（`pii/policy_globals_test.go`）——setup 阶段**同步**把
全局重置成缺省值；cleanup 把全局**同步**还原成缺省值，且**还原超时必须让用例失败**
（静默通过正是串扰的来源）；包内 **105 处**直接调 `Set*` 的写法全部改走 helper。

**证据**：基线 `go test ./pii/ -count=20` ⇒ **19 次红**（形态与登记逐字一致，main 上
逐字复现 ⇒ 预存在）；修后 `-count=20` **全绿**、`-race` 全绿；反向验证两处注入
（还原值改回旧约定 / 删掉 setup 重置）⇒ **都红**。两条护栏用例已入库
（`TestPolicyGlobalsSetupResetsToDefaults` / `TestPolicyGlobalsCleanupRestoresDefaults`）
——它们断言的是**注入的那一条被看见了**，不是「有违规」。

### 本轮的一条判据精度修正（合并时当场发现）

新规则落地后把 `eventbus` 的两处缺席断言**误判**成违规：那两处的「等待点」在助手
`assertNoTailFrame` 里，形态是 `select { case ev := <-ch: ...; default: }`——
这个 select **带 default 分支** ⇒ 它**永不挂起** ⇒ 这处接收**不等任何东西**，
它是**断言**（看此刻通道里有没有东西），不是 join。

按宽口径把它算成等待点，判据就会给出「把这个 drain 塞进 defer」的处方——而 drain
本来就不等东西，塞进 defer 什么也等不到 ⇒ **判据指错路**。

⇒ 修正：**非阻塞接收不算等待点**（走 `go/ast`：接收落在某个 select 的 CommClause 里、
且该 select 带 default 分支 ⇒ 非阻塞）。**双向用例钉住**：带 default 的 drain 不判红；
没有 default 的 select（带超时分支，仍会挂起）**仍判红**且必须点名用例名——
少一条，另一条就成了「判据瘫掉也绿」的假绿。

⚠ 兄弟规则 `harness-test-goroutine-joined` 仍用宽口径（任意接收表达式都算等待点）
——那是它的**已登记边界 1**，本轮不动（改它会把一批现存用例判红，属另一条登记行）。
